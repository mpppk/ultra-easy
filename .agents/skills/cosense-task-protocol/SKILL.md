# cosense-task-protocol

複数のエージェントセッションが、Cosenseの1ページで管理されたタスクを並行処理するための占有（claim）プロトコル。並行セッションが同じタスクに同時着手して重複実装・相互巻き戻しを起こすのを防ぐ。

CLIの実行形式・ページの読み方・編集ワークフローは `cosense` skill と `cosense <command> --help` に従う。本skillは**その上に乗る排他規約**だけを定める。

## 3つの層

| 層           | 実体                                                             | 扱い                                            |
| ------------ | ---------------------------------------------------------------- | ----------------------------------------------- |
| **権威**     | タスク行の子にある `🔒claim` 行                                  | claimの一次情報。着手可否の判定はここだけで行う |
| **索引**     | タスク行の行頭絵文字（📝 / ✅）                                  | 人間が眺めるための表示。ズレても事故にならない  |
| **実行ログ** | Cosenseのページ履歴（`browsePageChanges` / `listPageSnapshots`） | 自動で残る。**ページ本文に実行ログを書かない**  |

### なぜ絵文字をロックに使わないか

`cosense` の編集は `readPage` → `previewEdit` → `submitEdit` の3手だが、**compare-and-swapが効くのは `previewEdit` → `submitEdit` の区間だけ**である。

- `previewEdit` は `<projectUrl> <pageId>` と ops しか受け取らず、**commitIdを渡す引数が無い**。「自分が読んだ時点の状態」をサーバに伝える経路が存在しない
- したがって `readPage` → `previewEdit` の区間は無防備になる
- しかも `previewEdit` の戻り値は「自分のopsを適用した後のページ」なので、自分が `replace` した行には自分の書いた文字が写る。**直前に入った他人の書き込みは preview を見ても気付けない**

この区間で起きることは ops の種類で変わる。以下は実際に並行編集を再現して確認した結果である。

| その間に他エージェントが  | 自分の ops                        | 結果                                                                        |
| ------------------------- | --------------------------------- | --------------------------------------------------------------------------- |
| 対象行を**削除**した      | anchorに指定                      | **HTTP 422** で検知できる                                                   |
| 対象行を **replace** した | 同じ行を `replace`                | **エラーにならず、相手の書き込みを破壊する。preview出力にも競合が写らない** |
| 対象行を **replace** した | その行を anchor に `insertBefore` | 破壊しない。両方の行が残り、**preview出力に相手の書き込みが写る**           |

`previewEdit` 後にページが更新された場合は、`previewEdit` / `submitEdit` のどちらも `409 NotFastForward` を返す（こちらは確認済みで、レスポンスの `latest` に最新のページ状態が入る）。守られていないのはあくまで `readPage` → `previewEdit` の区間だけである。

**`replace` は奪い合いが起きる場所では使えない。`insertBefore` は破壊しないので、同時claimが起きても両方の行が残り、後から検知して決着できる。** だからclaimは行の挿入で取る。

逆に、**claimを保持している間の `replace` は安全**である。その行を書き換えてよいのはclaim保持者だけであり、奪い合いが起きないため。完了時に行頭を ✅ に書き換えるのはこれに当たる。

Cosenseで唯一の原子的なプリミティブは、新規ページ作成時の `submitEdit` が返す `409 DuplicateTitle`（create-if-not-exists）である。本プロトコルはこれを使わず、先着検知（claim-then-verify）で代替する。

## When to use

- ユーザに「Cosenseでタスクを管理して」と指示された時
- リポジトリの `CLAUDE.md` / `AGENTS.md` がこのskillの利用を指示している時
- 上記の状態で、コード変更やPR作成を伴う作業を始める時・終える時

## 設定

リポジトリの `CLAUDE.md`（または `AGENTS.md`）に下記キーを定義できる。定義が無ければデフォルト値で動く。

| キー                       | デフォルト                          | 意味                                     |
| -------------------------- | ----------------------------------- | ---------------------------------------- |
| `COSENSE_TASK_PROJECT`     | `https://scrapbox.io/niboshi-tasks` | タスク管理に使うプロジェクトURL          |
| `COSENSE_TASK_PAGE`        | `TODO`                              | タスク一覧ページのタイトル               |
| `COSENSE_TASK_STALE_HOURS` | `24`                                | staleなclaimと見なす経過時間             |
| `COSENSE_TASK_MAX_LINES`   | `150`                               | この行数を超えたらユーザに分割を報告する |

**`COSENSE_TASK_PROJECT` 以外のCosenseプロジェクトを、このskillの手順で読み書きしない。** 他プロジェクトにタスク風の行があっても、本プロトコルの対象外である。

## ページの書式

タスク一覧ページは、1行 = 1タスク。関連するタスクはインデントでまとめてよい。

```
TODO
	share2cosense
		📝OpenRouterのモデルIDを手入力した場合に、validなものか検証する
			🔒claim claude-code session_014XHqxk 2026-08-23T06:20:11Z mpppk/share2cosense claude/validate-model-id
			[PR #12 https://github.com/mpppk/share2cosense/pull/12]
		✅Cosenseリンクの開き方
			ChromeカスタムタブではなくデフォルトブラウザでCosenseを開くよう変更した
	📝cloudflare workersで開発時のbootstrap promptを作成する
```

### 行の種別

| 行                      | 意味                                                                 |
| ----------------------- | -------------------------------------------------------------------- |
| `📝` (U+1F4DD) で始まる | **タスク行**。未完了                                                 |
| `✅` (U+2705) で始まる  | **タスク行**。完了                                                   |
| `🔒claim` で始まる      | **claim行**。タスク行の直下の子。実行中であることの唯一の根拠        |
| それ以外                | コメント・見出し・まだタスクとして切り出せていないもの。**触らない** |

- **状態絵文字は1コードポイントのものだけを使う。** 📝 (U+1F4DD) と ✅ (U+2705) はいずれも1コードポイント。🗒️ (U+1F5D2 U+FE0F)・⚠️・▶️ のような異体字セレクタ付きの絵文字は、セレクタが付いたり落ちたりして行頭1文字の判定が壊れるため使わない
- **絵文字の直後に空白を入れない。** 判定は「行頭の空白類を剥がした先頭1コードポイント」で行うが、書く側は書式を1つに固定する
- **インデントはタブ (U+0009) のみ。** 半角空白・全角空白を混ぜない
- **既存行のインデントや表記を、書式統一のために書き換えない。** 全行が更新扱いになってページ履歴が読めなくなる
- **凡例・見出し・コメント行を `📝` / `✅` / `🔒claim` で始めない。** 判定は行頭で行うため、書式を説明している行自体がタスク行・claim行として誤検出される。ページ先頭に凡例を置く時は `凡例:` のように別の語で始め、本文中で `🔒claim` というリテラルに言及しない（`searchFullText` が拾ってしまう）

### 状態の判定

状態は保存せず、行頭絵文字と子行から**導出する**。

| 行頭 | 子に `🔒claim` | 状態                                                    |
| ---- | -------------- | ------------------------------------------------------- |
| `📝` | なし           | 未着手                                                  |
| `📝` | あり           | 実行中（claim行の executor が保持中）                   |
| `✅` | なし           | 完了                                                    |
| `✅` | あり           | **異常**（完了時の解放漏れ）。claim行を削除して修復する |

実行中を絵文字とclaim行の両方に持たせない。二重に持つと必ず食い違い、食い違った時の絵文字は**持ち主が分からない腐ったロック**になる。claim行なら executor と時刻を自ら名乗っているので回収できる。

### claim行の書式

空白区切りの固定順。値が無いfieldは `-` を書く。

```
🔒claim <agent> <session> <UTC ISO8601> <owner/repo> <branch>
```

- `<agent>`: エージェント種別（例: `claude-code`）
- `<session>`: セッション識別子。**同一プロジェクトのメンバーが1人でも、全エージェントが同じCosenseユーザとして書き込むため、Cosense側のユーザ情報では持ち主を識別できない。** claim行に書くのは必須であって任意ではない
- `<UTC ISO8601>`: `date -u +%Y-%m-%dT%H:%M:%SZ` で取得する
- `<owner/repo>` `<branch>`: 他セッションが「似た場所のコードを触っていないか」を判断する材料。タスク名だけでは判断できないので、リポジトリを触る作業では必ず書く

`🔒claim` は固定のリテラルなので、`searchFullText <COSENSE_TASK_PROJECT> '🔒claim'` でプロジェクト全体の実行中claimを1回の呼び出しで概観できる。他セッションの作業範囲を調べる時はこれを使う。

ただし**これは事前フィルタであって、着手可否の判定に使ってはいけない**。理由が2つある。

- **検索インデックスは編集に追従しない。** 編集直後に検索すると、更新前の本文がそのまま返る（実測で確認済み）
- **部分一致である。** 行頭でなくても、本文中で `🔒claim` に言及しているだけの行がヒットする

着手可否は必ず `readPage` で対象ページを読み、**「行頭が `🔒claim` であり、かつ対象タスク行の子である」**行だけを数えて判定する。

## タスクのclaim手順（claim-then-verify）

### 手順1: ページ全体を読む

`readPage <COSENSE_TASK_PROJECT>/<COSENSE_TASK_PAGE>` でページ全体を読む。

- top-level `id` を `previewEdit` の `<pageId>` に使う
- `lines[].id` を ops の anchor に使う
- **重複確認に `searchVector` を使わない。** ベクトル検索はタイトルと本文中のリンク記法しか対象にせず、完全一致の存在確認には使えない。1ページを丸ごと読むのが最も確実である

行数が `COSENSE_TASK_MAX_LINES` を超えていたら、作業は続けたうえで**ユーザに分割を報告する**。自動で分割・アーカイブしない。

### 手順2: 対象タスクを決める

- 対象タスク行の子に `🔒claim` 行があれば、**着手せず手順6（stale判定）へ**。踏み潰さない
- タスクがページに存在しなければ、先に「新しいタスクの起票」へ

### 手順3: claim行を insert する

claim行を、対象タスク行の**次の行**を anchor にして `insertBefore` する。既に子行があるなら最初の子の直前、タスク行がページ末尾なら anchor に `_end` を指定する。インデントはタスク行 + タブ1つ。

```json
{
  "ops": [
    {
      "insertBefore": "<タスク行の次の行のlineId | _end>",
      "text": "\t\t\t🔒claim claude-code session_014XHqxk 2026-08-23T06:20:11Z mpppk/share2cosense claude/validate-model-id"
    }
  ]
}
```

`previewEdit` の出力を確認してから `submitEdit` で確定する。**タスク行そのものには一切触らない。**

タスク行を `replace` しないので、**preview出力にはその時点のサーバ上のタスク行がそのまま写る**。ここに他セッションのclaim行が既に見えていたら、submitせずに手順6へ分岐する。これはsubmit前に競合を潰せる唯一の機会である（`replace` を使うと自分の書いた文字で上書きされ、この検知ができない）。

### 手順4: 再読して検証する

submit成功後、**もう一度 `readPage` する**。対象タスク行の子にある `🔒claim` 行を全部数える。

| 見えたもの          | 行動                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------ |
| 自分のclaim行だけ   | claim成立。手順5へ                                                                         |
| 複数のclaim行       | **タイムスタンプが最も早いものが勝ち。**同時刻ならセッション識別子の辞書順で小さい方が勝ち |
| 自分のclaim行が無い | 他セッションに回収された。別のタスクへ移る                                                 |

負けた場合は、**自分のclaim行だけを `delete`** して、次の候補タスクへ移る（先着優先・バックオフ）。同じタスクで粘らない。他人のclaim行には触らない。

### 手順5: 作業する

- **同時に保持してよいCosense claimは1つ**（WIP制限）。次のタスクをclaimする前に、現在のclaimを完了または解放する
- PRを作成したら、claim行の次に子行として `[PR #<番号> <URL>]` を追記する。**ラベル付きの外部リンク記法にする**。`#12` のような裸のPR番号は Cosense のhashtag記法として解釈されるため、必ずラベル内に収めるかバッククォートで囲む
- **進捗報告のための書き込みをしない。** heartbeatは実装しない（後述）
- PRリンク追記のように**別の理由で書き込む時に限り**、ついでにclaim行のタイムスタンプを現在時刻へ更新してよい。そのためだけに書き込まない

### 手順6: staleなclaimの判定

セッションはコンテナ回収等で予告なく死ぬため、放置されたclaimは回収してよい。ただし**本プロトコルにheartbeatが無いため、claim時刻の古さは「死んでいること」の証拠にならない**。長時間の作業が正常に継続している場合と区別が付かない。

したがって:

- `COSENSE_TASK_STALE_HOURS`（デフォルト24）を超えたclaimを**stale候補**とする
- **自動で奪わない。ユーザに確認してから回収する。** 誤回収による重複実装のほうが、待つより高くつく
- 回収する場合は、**1回の `previewEdit` で** 他人のclaim行を `delete` し、自分のclaim行を `insertBefore` する。その後、手順4の検証を行う
- 閾値に満たないclaimは、進捗が見えなくても上書きしない

## 完了・中断

### 完了

**1回の `previewEdit` にまとめて**、以下を順に行う。ops は配列順に適用され、anchor は適用時点で存在している必要がある。

```json
{
  "ops": [
    { "insertBefore": "<自分のclaim行lineId>", "text": "\t\t\t作業の要点を数行で" },
    { "delete": "<自分のclaim行lineId>" },
    {
      "replace": "<タスク行lineId>",
      "text": "\t\t✅OpenRouterのモデルIDを手入力した場合に、validなものか検証する"
    }
  ]
}
```

- `insertBefore` を `delete` より先に置く。逆順にすると anchor が消えていて 422 になる
- `replace` に渡す text は**単行のみ**。改行を含めると拒否される
- タスク行のインデントと本文は変えない。**行頭の絵文字だけを 📝 → ✅ にする**

要点は数行で書く。**書くことが多いと判断したら、独立したページを新規作成してタスク行の子からリンクする**（`[ページタイトル]`）。他プロジェクトのページを参照する時は `[/niboshi-private/ページ名]` の形式を使う。

**✅ の定義: このセッションでやると決めたことが終わった状態。** PRのマージは条件に含めない（マージは人間とCIの仕事であり、エージェントのclaimはPRを出した時点で解放されるべきである）。マージ待ちであることは、PRリンクを見れば分かる。

### 中断・撤退

作業を断念する、コンテキストが尽きる、ユーザに中止されたなど、**完了せずに手を引く場合は必ず claim行を `delete` する**。タスク行は 📝 のまま残り、未着手に戻る。

```json
{
  "ops": [
    { "insertBefore": "<自分のclaim行lineId>", "text": "\t\t\t2026-08-23 中断: <理由>" },
    { "delete": "<自分のclaim行lineId>" }
  ]
}
```

**黙って放置しない。** 解放されなかったclaimは、次のセッションが `COSENSE_TASK_STALE_HOURS` 待たされる原因になる。

## 新しいタスクの起票

ページに存在しない作業を依頼された場合は、タスク行を起票してからclaimする。

### 起票する / しない

| 起票する                       | 起票しない                                   |
| ------------------------------ | -------------------------------------------- |
| コードを変更する作業           | 調査・質問への回答・要約                     |
| PRを作成する作業               | 単発のコマンド実行、ファイルを読むだけの作業 |
| 複数セッションに跨がりうる作業 | 既存タスクの一部として進む作業（子行に書く） |

**ユーザの依頼1件 = タスク1件**を目安にする。エージェントの実行回数ぶんタスクを作らない。リトライで新しいタスクを起票せず、既存のタスク行を再利用する。

### 手順

1. `readPage` でページ全体を読み、**同じ内容のタスクが既に無いか確認する**
2. 関連する既存タスクがあれば、その子として `insertBefore` する。無ければトップレベルに追加する
3. 起票とclaimは**別々の `previewEdit` で行う**。1回にまとめると、起票だけ通ってclaimが失敗した時の状態が分かりにくくなる。起票を先に確定し、そのうえで claim手順（手順1から）をやり直す

## 編集が衝突した時

### HTTP 409 NotFastForward

`previewEdit` 生成後にページが更新された。

1. **古い ops / previewId を再送しない。** その間に入った他セッションの書き込みを消す
2. `readPage` からやり直し、lineId を取り直して ops を組み直す
3. **claim対象の状態を再確認する。** 既に他セッションの `🔒claim` 行が付いていたら手順6へ分岐する
4. 再試行は**最大3回**まで。それを超えたらユーザに報告して止まる

ページ単位のCASなので、**別々のタスクをclaimしているセッション同士でも409は起きる**（偽の競合）。その場合は再読して同じopsを組み直せば通る。

### HTTP 422

ops が現在のページ状態に対して不正。anchor に指定した lineId が消えている可能性が高い（他セッションがその行を削除した）。`readPage` からやり直す。

### HTTP 404 / 401 / 403

- 404: `pageId` が現在のページを指していない。`readPage` からやり直す
- 401 / 403: 認証・権限の問題。同じリクエストを繰り返さず、`cosense` skill の login手順を参照する

## issue-claim-protocol との併用

両方のskillが指定されている場合、**2つの規約は互いに干渉せず、並列に運用する**。

- **どちらも独立して claim を取り、独立して解放する。** GitHub側のclaim（Draft PR）が失われても Cosense のclaim行はそのまま有効であり、逆も同じ。片方の状態からもう片方を推測しない
- **finalizer は両方走らせる。** 作業を終える時は、issue-claim-protocol の後始末（ラベル除去・ready化）と、本skillの完了手順（claim行削除・✅化）を**どちらも**実行する
- **WIP制限は別カウント。** 「Cosense claim 1件」と「Issue claim 1件」は同時に成立してよい
- **機構を輸入しない。** issue-claim-protocol の `last-heartbeat` / `lease-until` / `attempt` / `status` 語彙を Cosense側に持ち込まない。理由は次節
- **リンクは Cosense → GitHub の一方向のみ。** タスク行の子にPRのURLを書く。逆に **PRの本文やコメントにCosenseのURLを書かない**。タスク管理プロジェクトは非公開であり、公開リポジトリのPRに書いても他者には開けず、非公開URLを露出させるだけである

## やってはいけないこと

- **heartbeatを実装しない。** Cosenseでは1回の更新が1コミットになり、ページ履歴（snapshot）を汚し、書き込みのたびにCASの衝突機会が増える。生存確認のためだけにページを書き換えない。stale判定は claim時刻と `COSENSE_TASK_STALE_HOURS` だけで行う
- **実行ログをページに書かない。** 誰がいつ何を変えたかは `browsePageChanges` / `listPageSnapshots` が既に持っている。ページに残すのは claim / PRリンク / 完了の要点 / 中断理由 の4種類だけ
- **完了タスクを自動でアーカイブしない。** 行数超過はユーザに報告するだけにする
- **状態を増やさない。** ブロック中・レビュー待ち・担当・期限・見積もりのような欄を足さない。誰も更新しない欄が増えるだけである。ブロックされたら claim を解放し、理由を子行に書く
- **`COSENSE_TASK_PROJECT` 以外のプロジェクトを、この手順で読み書きしない**
- **既存行を書式統一のために書き換えない**
- **ユーザが書いた行を書き換えない。** 追記は子行として行う

## CLAUDE.md への記載例

リポジトリ側に以下を書くと、そのリポジトリでの作業時にこのskillが使われる。

```markdown
## タスク管理

作業は `cosense-task-protocol` skill に従い、Cosenseでタスクとして管理する。設定:

- COSENSE_TASK_PROJECT: `https://scrapbox.io/niboshi-tasks`
- COSENSE_TASK_PAGE: `TODO`
- COSENSE_TASK_STALE_HOURS: `24`
```

skillは**プロンプトと文脈で発火するのであって、リポジトリのファイル内容を監視して自動的に起動するわけではない**。上のように「このskillに従う」と明示的な指示文の形で書く必要がある。

## 厳密な排他が必要になったら

本プロトコルは先着検知のbest-effortであり、`readPage` → `previewEdit` の区間に残る競合を「insertは破壊しない」という性質だけで吸収している。同時claimが頻繁に起きるようになったら、タスクを1件1ページに分割して新規ページ作成の `409 DuplicateTitle`（create-if-not-exists）を本物のmutexとして使う設計へ移る。その場合、タスク一覧ページは索引に降格し、本skillはページ単位のclaim手順に置き換わる。
