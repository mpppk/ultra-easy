# Cosenseプロジェクト セットアップ手順（管理者向け・1回だけ）

タスク管理に使うCosenseプロジェクトを用意する。claimプロトコル本体は [SKILL.md](SKILL.md)。

## 1. 専用プロジェクトを用意する

タスク管理には**専用のプロジェクトを1つ切る**（例: `niboshi-tasks`）。既存のリサーチwikiに相乗りしない。

- リサーチwikiには「タスク風の行」が本文中に散らばりうる。専用プロジェクトなら、`COSENSE_TASK_PROJECT` の外を一切読まないという境界を単純に引ける
- `searchFullText <project> '🔒claim'` が、実行中claimの概観になる（インデックス遅延と部分一致があるため事前フィルタ止まり。詳細は SKILL.md）。混在プロジェクトではさらにノイズが乗る
- `listPages --sort updated` が、そのままタスクの更新順一覧として使える

## 2. メンバー構成の含意を確認する

`listProjects` の `usersCount` を見る。

**メンバーが1人（個人プロジェクト）の場合、全エージェントが同一のCosenseユーザとして書き込む。** ページ履歴の「最終更新者」からはロックの持ち主を識別できない。これが SKILL.md で claim行に `<agent>` と `<session>` を書くことを**必須**にしている理由である。任意項目にしない。

## 3. タスク一覧ページを作る

`previewEdit --new <projectUrl>` に、1行目をページタイトルとしたプレーンテキストを渡す。インデントは**タブのみ**を使う。

```
TODO
	このページはAIエージェントのタスク管理に使う。書式は cosense-task-protocol skill に従う。
	凡例: 📝=未完了 / ✅=完了 / タスク行の子にある 🔒 で始まる行 = 実行中のセッション
	ロック行は作業を終えた時・中断した時に必ず消すこと。消し忘れると次のセッションが待たされる。
```

ページ先頭に書式を書いておくと、`cosense` skill の編集手順が「編集対象ページをまず読む」段階でこれを拾う。人間にとっての凡例にもなる。

**凡例の行を `📝` / `✅` / `🔒claim` で始めてはいけない。** 状態の判定は行頭で行うため、書式を説明している行自体がタスク行・claim行として誤検出される。同じ理由で、凡例の文中に `🔒claim` というリテラルを書かない（`searchFullText` がその行を拾う）。上の文面はこの2点を避けてある。

**最初から満杯にしない。** タスクは必要になった時に起票する。

## 4. 既存のTODOを移行しない

別プロジェクトに既存のTODOページがある場合、**中身を機械的に移さない**。

- 既存ページはインデント文字（半角空白・タブ・全角空白）や絵文字直後の空白が揺れていることが多い。移すと、その揺れを許容するパーサが恒久的に必要になる。**新しいプロジェクトを、書式が1つに固定された状態で始められるのが最大の利点である**
- 完了済みの行を移す価値はない。履歴は元のプロジェクトに残っている
- 移すのは**未完了のタスクだけ**にし、書式を整えながら**手で**入れ直す

旧プロジェクトを触らない方針にした場合は、そのまま放置してよい。ただし **`COSENSE_TASK_PROJECT` は新しいプロジェクトを指すこと**を確認する。指し先が古いままだと、エージェントは旧ページを正本として読み書きする。

## 5. 行数が増えてきたら

`COSENSE_TASK_MAX_LINES`（デフォルト150）を超えると、エージェントがユーザに報告する。**自動では何も起きない。**

分割する場合は、完了済みタスクを別ページ（例: `TODO-DONE-2026`）へ移し、一覧ページには未完了タスクだけを残す。移動は人間が行う。エージェントに自動アーカイブさせない — 完了の記録が本人以外の判断で移動すると、PRからタスクへ辿れなくなる。

1ページの全読みが重くなってきたことが分割の本当の理由であって、見た目の問題ではない。claim手順は毎回ページ全体を読むので、行数はそのままレイテンシとトークン消費になる。

## 6. 動作確認

セットアップ後、1件だけ実際に流して確認する。

1. タスクを1件起票する
2. claimを取る → `readPage` で `🔒claim` 行が1本だけ入っていること
3. `searchFullText <projectUrl> '🔒claim'` で、そのタスクが引けること（インデックス遅延があるので、すぐに出なくても異常ではない）
4. 完了させる → 行頭が ✅ になり、`🔒claim` 行が消えていること
5. `browsePageChanges` で、1〜4が個別のコミットとして残っていること

4で `🔒claim` 行が残るのが、運用上いちばん起きやすい事故である。残っていたタスクは、次のセッションから「実行中」に見え続ける。

## 注意

- **`replace` は lineId を保存する**（実測で確認済み）。ただし SKILL.md の手順は毎回 `readPage` で lineId を取り直す形にしてあり、この性質に依存していない。lineId をタスクの永続IDとして外部（PR本文など）に書き出す運用を足す場合だけ、この性質が前提になる
- `previewId` は5分でexpireし、submitで消費される。`previewEdit` と `submitEdit` の間に長い思考を挟まない
- タスク一覧ページを**リネームしない**。リネームすると被リンクが切れ、`COSENSE_TASK_PAGE` の設定とも食い違う
